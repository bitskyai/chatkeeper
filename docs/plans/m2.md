# M2 implementation plan

The approved architecture sections 7–11 and issue #2 define the design: one
browser application, platform-owned setup steps, YAML as the source of truth,
and app-state SQLite. No alternative frontend or ORM is needed.

1. Add secret resolution, atomic comment-preserving configuration updates, and
   a serialized runtime manager. Verify reload additions, removals, changes,
   invalid retention, and credential-specific restarts.
2. Add numbered SQLite migrations, server/desktop authentication and CSRF/Host
   boundaries. Test bootstrap lock, session requirements, rate limiting and
   write-only credentials.
3. Implement platform setup steps and registry placeholders; render schemas and
   steps generically. Test named scope errors, tokens and channel membership.
4. Wire browser startup, instance ownership, file/SIGHUP reload, dashboard,
   settings, storage commit and live archive polling.
5. Add chromedp end-to-end coverage in both modes against the fake API, save
   synthetic screenshots, add dedicated CI and README desktop instructions.
6. Run race, architecture, static analysis, cross builds and security checks;
   review the complete diff, open the requested PR and resolve CI failures.

Review focus: bootstrap after database loss; path symlinks; secrets in persisted
wizard state; requests with hostile origins; runtime shutdown before store close.
