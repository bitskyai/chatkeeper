# M3 search, REST and MCP implementation plan

**Goal:** Implement issue #3 using the approved architecture §§6.3 and 12.
**Architecture:** Verified archives remain authoritative. Per-workspace unicode61 FTS5 indexes contain current and retained historical text. A shared service owns filters, ranked pagination and safe errors; REST and official SDK MCP adapters expose only reads.
**Tech stack:** Go, modernc SQLite, official MCP Go SDK.
**Spec:** docs/design/architecture.md and issue #3.

## Constraints and review focus

No platform knowledge in core; no credentials or filesystem locations in responses.
Missing/corrupt/stale indexes rebuild without changing archive content. Lock order
is service → archive → index; capture releases archive lock before notifying search.
Read APIs must never return binary attachment content or initialize live sessions.
Cursors bind the query and index revision; edits invalidate them. Schema-2 history
remains searchable and flagged. HTTP MCP requires bearer auth and same-origin checks.

## Tasks

1. Storage/search: add locked verified archive traversal; test bootstrap, filters,
   unicode/ranking, pagination validation, rebuild, never-drop history and concurrent
   capture/rebuild; run failing tests, implement index/service, rerun tests.
2. Runtime/REST/UI: initialize service before capture, sync after all archive writes
   including no-op repair and root deletion; test authenticated REST errors,
   pagination, thread JSON and dashboard/viewer search; implement and verify.
3. MCP: test real SDK clients over stdio and HTTP plus golden JSON-RPC transcript;
   implement three read-only tools, authenticated transport, offline CLI.
4. Verification/docs: port reference cases and document deviations, record 10k
   rebuild/query benchmark, run race/noplatform/vet/staticcheck and browser tests,
   review branch, push PR with Closes #3 and follow every existing CI job to green.
